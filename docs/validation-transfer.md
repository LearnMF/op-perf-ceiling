# 用已有卡上的实测换算到另一张卡：能到多准（gfx936 ↔ gfx938）

> 问题：新算子、新硬件时，能不能「先在我们有的卡上跑一下（开源实现即可），再换算到目标卡」？
> 数据（2026-11-13，两张卡各自实测 fwd+bwd 设备时间）：
> - FLA 0.5.2（Triton）KDA，27 个形状；FLA GDN，issue #29 的 15 个形状（含 H ≠ HV）——`bench/fla_bench.py`
> - flash-train mk3 KDA（两张卡各自优化到位的版本），27 个形状——`bench/kda_bench.py`
>
> 复现：`python -m opceil transfer`；完整表：`reports/transfer_gfx936_gfx938_20261113.transfer.md`。

## 1. 同一实现跨卡（FLA KDA：用 gfx936 实测预测 gfx938，反向同理）

| 换算比例从哪来 | 误差中位（936→938 / 938→936） | 最大 |
|---|---:|---:|
| 规格：算力峰值之比 | 44% / 31% | 73% / 42% |
| 规格：带宽之比 | 24% / 32% | 32% / 46% |
| **本工具的模型比例**（逐形状 `T_split` p82 之比） | **26% / 35%** | 34% / 52% |
| 同一算子另一实现（mk3）的实测比例 | 11% / 12% | 20% / 25% |
| **同族另一算子（FLA GDN）的实测比例，整体** | **4.8% / 4.6%** | 24% / 19% |
| 同上，按 kernel 模式分别换算 | 4.5% / 4.9% | 22% / 19% |

## 2. 「新算子」跨卡（FLA GDN：只用它在一张卡上的实测，加上 FLA KDA 在两张卡上的比例）

| 换算比例从哪来 | 误差中位（936→938 / 938→936） | 最大 |
|---|---:|---:|
| 规格：算力峰值之比 | 40% / 28% | 68% / 40% |
| 规格：带宽之比 | 26% / 36% | 37% / 59% |
| **FLA KDA 的实测比例，整体** | **8.9% / 9.7%** | 17% / 21% |
| FLA KDA 的实测比例，按 kernel 模式 | 8.5% / 16.6% | 24% / 44% |
| 参照：GDN 自己的比例（留一个形状） | 9.2% / 9.5% | 21% / 19% |

## 3. 「手工优化能提升多少」能不能跨卡沿用

FLA / mk3 的耗时比：gfx936 中位 **2.07**（1.88–2.41），gfx938 中位 **2.33**（1.93–2.63）——同一算子，优化收益在两张卡上差 12%。
用「目标卡上的 FLA 实测 ÷ 参考卡上的优化倍数」去估目标卡上的 mk3：误差中位 10.6% / 9.6%，最大 27% / 21%。

## 4. 结论

1. **实测比例远比模型比例和规格比例准**：同一个库里同族算子的跨卡比例，拿来换算另一个算子，误差中位 5–10%；
   规格比例 24–44%，本工具的模型比例 26–35%（模型把 KDA 判成显存受限，于是按带宽之比换算，方向就偏了）。
2. **按 kernel 模式拆开换算没有比整体换算更好**：同一模式在 FLA KDA 和 GDN 里的跨卡比例并不一致
   （out_fwd 0.58 对 0.94，bwd_wy_dqk 0.57 对 0.76），因为是不同的 kernel 实现；模式库要按「实现」建，不只按算法模式。
3. **手工优化的收益跨卡会变**（2.07 → 2.33）：「开源实现 ÷ 优化倍数」估优化后水平，误差约 10%，最坏 20–27%。
4. **前提必须讲清楚**：这里的比例是在**两张卡都能跑**的条件下学到的。对一张完全没法跑的未知硬件，比例从哪来才是关键：
   - 本工具现在的模型比例不行（26–35%）；
   - 可行的来源是：在目标硬件的 SOC/EMU 仿真（或早期样片）上跑**少数几个锚点 kernel**（例如 PV 表那样的 GEMM / attention / 递推类），
     得到各自的实测比例，再把同族算子按这些比例换算——第 1、2 节说明这一步本身能到 5–10%。

注：报告里不列 `T_bound` 的比例：gfx936 用手册带宽、gfx938（无手册值）用实测带宽，两种口径混在一起，比值与实测碰巧接近（约 4%），
统一用实测带宽时它就是上表「带宽之比」那一行（约 24%）。
