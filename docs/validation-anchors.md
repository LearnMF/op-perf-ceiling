# 未知硬件：用少量锚点 kernel 预测（PV 表 S4000 / S2000 的 SOC 仿真结果当真值）

> S4000 / S2000 没有卡，SOC 仿真结果（`data/pv/pv_soc_sim_20261016.xlsx`，曹媛媛 10-23）当真值。复现：`python -m opceil anchors`，
> 报告 `reports/anchors_pv_s4000_s2000.anchors.md`。

## 1. 同一类算子：目标卡上 3 个锚点 + L0 Roofline（GEMM）

每张卡从 16 行 GEMM 里按形状（不看耗时）选锚点：1 个固定开销型（M ≤ 2、N·K 小）、1 个访存型（M ≤ 2、大权重 bf16）、1 个算力型（fp8、M ≥ 4096），
由它们得到这张卡的「有效机器」（固定地板、流式带宽、fp8 算力），再用 `max(地板, 字节/带宽, 计算量/算力)` 预测其余 13 行。所有锚点组合都试（每卡 24 种）：

| 卡 | 误差中位（各组合的中位） | 最差组合的中位 | 典型最大误差 |
|---|---:|---:|---:|
| S4000 | 11.4% | 30.0% | 39.9% |
| S2000 | 10.9% | 14.1% | 39.4% |

## 2. 跨算子族：用 GEMM 锚点的比例把 S2000 换算到 S4000

S4000/S2000 的实测耗时比：GEMM 访存型 0.60、算力型 0.46；**DSA 0.59–0.90（中位 0.79）；MoE 0.71–0.86**——不同算子族对硬件变化的敏感度差很多。

| 用哪个比例 | DSA 误差中位（14 个配置） | MoE 误差中位（5 个配置） |
|---|---:|---:|
| GEMM 固定开销锚点（1.01） | 27.2% | 26.6% |
| GEMM 访存锚点（0.60） | 23.9% | 24.3% |
| GEMM 算力锚点（0.46） | 42.0% | 42.3% |
| GEMM 整体中位（0.62） | **21.5%** | **21.9%** |
| 什么都不换算（1.0，相当于「一刀切」） | 26.3% | 25.7% |
| MoE：L0 模型按两卡各自的 EP（8 / 16）归一化后换算 | — | **51.4%（更差）** |
| **同族锚点**：用 DSA / MoE 自己其它配置的比例（留一法） | **12.0%**（最大 39%） | **9.9%**（最大 16%） |
| 同族只用 1 个锚点（DSA batch 1） | 18.0% | — |

## 3. 结论

1. **同一类算子，在目标硬件上有 3 个锚点，L0 Roofline 就能把整族预测到约 11%**（GEMM）。这是工具在未知硬件上真正起作用的方式：
   用公式把少量锚点「铺开」到整个 shape 空间。
2. **锚点不能跨算子族用**：GEMM 锚点换算 DSA / MoE，误差 22–24%，和完全不换算（26%）差不多。每个算子族都要有自己的锚点；
   有了同族锚点，误差回到 10–12%（与 gfx936↔gfx938 上 FLA KDA/GDN 的 5–10% 一致）。
3. **数据口径不清时，模型会把结果变差**：MoE 两张卡用了不同的 EP（8 对 16），按「token 全局、均匀路由、不含通信」去归一化后误差从 22% 变成 51%——
   说明 `num_tokens` 的含义或 `sim_total_us` 是否含 EP 通信与假设不符（PV 资料里本来就标了待确认）。这类问题脚本发现不了，需要人或 AI 去追口径。
